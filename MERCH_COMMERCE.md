# Merchandise and commerce

The runtime catalog is database-backed. Owner MFA is required to create/edit/duplicate/archive products and configure images, publication, featured status, SEO, options, variant-specific prices and stock. Duplicate creates a draft with unique SKUs and zero stock. Product saves are atomic and version checked. Constraints reject invalid amounts, negative stock, duplicate SKUs, invalid paths and cross-product variant reassignment. Removed variants remain unavailable records for order integrity.

Money is integer PHP centavos. Decimal input is parsed from strings; order totals use database bigint arithmetic. The four imported source catalog IDs and asset paths remain stable for old browser bags. Uncounted stock is explicitly unknown. The storefront keeps its existing appearance, option selection and local cart; stale prices, unavailable options/products and excess quantities are surfaced and excluded appropriately. No public checkout is enabled.

Sandbox order preparation is service-only and idempotent. It reads current sellable variant prices and confirmed inventory, snapshots names/SKUs/unit amounts, and ignores client price claims. It does not reserve or decrement inventory. Confirmation requires a trusted server caller, matching provider session/payment, total and event identity. Confirmed payment decrements stock exactly once; stale product editors are invalidated by stock changes. Parent products are locked before variants to prevent lock-order inversions.

Fulfillment progresses unfulfilled → processing → shipped → delivered for paid/partly refunded orders. Cancellation is limited to unfulfilled/processing records with unpaid/failed/expired/refunded payment states. Notes are internal; payment state is not an admin field. Refund reconciliation accepts only trusted, monotonic cumulative refund evidence, validates the payment reference and does not automatically restock goods. Sales deduct verified merch refunds; membership receipts remain separately labeled. CSV export excludes internal notes and payment payloads and has an explicit 1,000-row cap.

Product photos are chosen from reused merchandise assets and up to 50 matching public uploads. Search and selection use native controls; uploading reuses the existing decoded-image endpoint. The uploader is a separate form and never silently publishes a selected photo or product. Removing an association retains the original file.

Database triggers lock selected public media in a consistent order before a product save. Referenced merchandise images cannot be revoked, moved to a private bucket or deleted, including through the older media cleanup RPC. An owner must change the product photo association first. A GIN index supports the gallery-reference check. Rejected or deletion-prepared media cannot be reattached; concurrent saves and cleanup serialize on the media row.

Production blockers: merch checkout activation, complete shipping/tax/fulfillment and reservation policy, real sandbox/provider end-to-end acceptance, and a dedicated merch webhook reconciliation adapter. Existing PayMongo membership sandbox signature verification, remote provider verification and replay protection remain intact. No live charges or provider switches occurred.
